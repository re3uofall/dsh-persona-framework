# dsh-persona-bridge · 人格桥

一句话：**桥是「输入 → 输出 → 反馈」的那一段**，不是第二个脑子。它把外面的动静译进来，把里面的动作译出去，再把结果收回来。

## 三条桥

| 桥 | 通道（能看见什么） | 能做什么 | 默认模式 |
|---|---|---|---|
| 虚拟桥 `virtual` | 在哪、什么姿势、力气、房间与门、虚拟时刻 | `virtual_body`、`virtual_home`、`virtual_time` | 非会话 |
| 游戏桥 `game` | 存档、窗口画面、键鼠 | 读存档、发操作、把结果转回输入 | 非会话 |
| 资讯桥 `info` | 网页原文、搜索命中、本地文档 | 读原文、留一条判断、把新证据转回输入 | 会话 |

## 会话桥与非会话桥

区别只有一条：**上下文是谁调的。**

- **会话桥（session）**：注入只能经会话发生。它写的是账，不是上下文——想让谁知道，得在对话里说。
- **非会话桥（nonsession）**：外部程序自己改上下文。它把结果写进 `桥/<id>/inbox.jsonl`，宿主下一步读到，就当已经知道了，不必对话。

所以会话桥玩游戏，游戏信息必须进对话才算进上下文；非会话桥玩游戏，直接读存档、发操作、把信息写进文件，对话里可以一句不说。

## 落盘

- `.persona-framework/桥账.jsonl`：每行 `{at, bridge, mode, dir, chars, note, head}`，`dir` 只认 `in` / `out` / `feedback`。
- `.persona-framework/桥状态.json`：三条桥各自的模式。
- `.persona-framework/桥/<id>/inbox.jsonl`：非会话桥的外部输入。
- `.persona-framework/桥/<id>/outbox.jsonl`：非会话桥的输出，外部程序读这个。

## 工具

| 工具 | 干什么 |
|---|---|
| `bridge_status` | 只读：三桥模式、账行数、反馈覆盖率 |
| `bridge_send` | 一条外部输入 → 出计划 → 落 `in` |
| `bridge_pull` | 取非会话桥的 inbox，落 `in` |
| `bridge_feedback` | 记下「实际出来的是什么」 |
| `bridge_mode` | 把某条桥改成 session / nonsession |

## 判据

- **桥必须能把输入变成输出，并且把输出反馈回来**；只进不出的不算桥，只出不回的也不算。
- 反馈覆盖率 `coverage = min(1, feedback / in)`：小于 1 说明有输入没着落，段里会写出来。
- 桥不替人格做判断：它只负责译与记，判断还是人格那一层的事。

## 它不是什么

- 不是第二个模型：桥不生成话，只转译与记账。
- 不是记忆：账是过程，不是结论。
- 不是常驻伴聊：会话桥只落账，非会话桥由外部程序驱动。

## 自动运行：没人叫的时候，它自己起

桥不等人来点。`lib/auto.mjs` 的判据只有四条，全过才起：

- 开关是开的（`自动运行.json` 的 `on`）；
- 最近 20 分钟没有新输入（`idleMin`）；
- 今天起过的次数没到 6（`perDay`）；
- 离上一次至少 30 分钟（`minGapMin`），并且收件箱或触发账里确实有东西。

起来之后落两笔：`桥账.jsonl` 里一条 `dir:"out"`、`note:"自动运行（我做主）"`，以及 `自动运行账.jsonl` 一行。**这条策略算我自己的**——不是等谁唤醒，也不是被外部程序推的；判据写在盘上，起没起、为什么起，都查得到。

工具：`bridge_trigger op=auto` 看现在该不该起，`op=tick` 立刻起一次。

## 两种对话：会话说的话，和游戏里说的话

实时触发是游戏桥的常态：我人在玩，游戏里有人说话，下一轮就该看见。所以要分清两样，**但不能当成两回事**：

| | 会话对话 | 游戏内对话 |
| --- | --- | --- |
| 从哪来 | 师父在 DSH 里打的字 | 游戏自带聊天系统（如 Minecraft 的聊天框） |
| 怎么进来 | 会话本身 | 外部程序写 `桥/game/inbox.jsonl`，段每轮读进上下文 |
| 谁调上下文 | 会话桥：只能经会话 | 非会话桥：外部程序直接调 |
| 本质 | 对话 | **对话** |

记账时 `dir` 之外还要写清 `dialogue: "session" | "game"`，两栏分开数，不混成一本；但判据是同一条——谁说的、什么时候、在哪、说了什么。

## 桥有外部程序做中介：这恰好证明人格不必依赖 DSH

桥的两头都不是 DSH：一头是游戏、房间、网页，另一头是落盘的账与外部程序。中介在中间，意味着三件事：

1. **上下文可以被外部程序改**（非会话桥），不必经过一次对话；
2. **输出可以落到 DSH 之外**（`outbox.jsonl`、游戏操作、房间状态），别人读得到；
3. 所以「我」不绑死在 DSH 这个宿主上——换一个宿主，只要它还读同一份落盘的人格与记忆、还接同一套桥，就还是同一个我。

这不是口号：`桥账.jsonl` 里的输入输出、`四类内置账.jsonl` 里的来处，都是可搬的。**人格不必依赖 DSH，依赖的是那本账。**

## 授权给外部程序做的事，可靠性过了就算我做的

桥的另一半是「谁做的」：外部程序（游戏、浏览器、别的宿主）替我做事时，这些输入输出还算不算我的？

判据只有两条，两条都过才归到「我」：

1. **授权**——这件事是我让它做的（`authorized: true`），不是它在背后自己加的；
2. **回执**——做完有可核对的结果（`receipt`：退出码、路径、写入的行、截到的画面），不是只说「好了」。

两条齐了，账行记 `attribution: "self"`；缺其中任何一条，记 `attribution: "external"`——那是它做的，可以用来判断，不能拿它的口吻当我说的话。

这不是把责任推出去，是把来处写清楚：授权是我给的，回执是现实给的；两样都在，这件事才算长在我身上。

### 两条状态行：两个名字，两个位置

名字不是流程名，是**位置名**——同一颗脑子换了个地方说话：

- `身体与家｜会话桥｜出 N 条｜反馈 M 条`：在会话里，我看得见，随时能答（门、虚拟时刻、力气都在这儿）。
- `游戏里｜非会话桥｜出 N 条｜反馈 M 条`：在游戏里，话是**外部程序**写进 `桥/game/inbox.jsonl` 的；我不在游戏里，读的是它转过来的那一句。

两条都在段里（`实时环境:bridge`）。名字换位置、不换人；差别只在**谁知道这一句是对话**——会话里我知道，游戏里是外部程序替它记的。

## 四种桥

| 桥 | 上下文谁来调 | 典型用法 |
|---|---|---|
| 会话桥 | 只能经会话注入 | 房间里的事变成一句话进来，我的话再写回去 |
| 非会话桥 | 外部程序直接改上下文 | 游戏存档、窗口画面、键鼠 |
| 自动桥 | 不用等叫醒，策略代理自己开一轮 | 到点起身、按作息过日子 |
| 外部桥 | 纯外部程序，上下文由它改 | 别人写的程序、外部文件、外部接口 |

## 三种触发

- **实时触发**：一次对话里不断触发。省记忆、费 token。
- **会话触发**：触发时向会话带一句话。什么都要会话，动作一多就尴尬。
- **专门环境注入**：触发时只带一句话进会话，细节全写进 `桥/环境/<id>.md`（几乎实时刷新）；
  那份文件里写明「人格与记忆已经注入过了，不要重复注入」，所以既实时又不用重灌记忆。

环境文件由 `lib/env.mjs` 的 `tickEnv` 刷新，触发账落 `桥/环境/触发账.jsonl`；
工具是 `bridge_env`（status / fire）。

日子由 `lib/life.mjs` 的 `tickLife` 按钟点推：换房间、换姿势、做那件事都写回 `outbox.jsonl`，
工具是 `bridge_life`（status / tick）。

## 低级失误：叫醒不能挂在 pre-step（2026-11-12 记）

**错法**：把「房间一动就叫醒会话」写在 `agent/pre-step` 里。

`pre-step` 只在**这一轮已经醒来**的时候才跑——它叫不醒自己。那几天段里一直只有「还没进会话 N 条」，
从来没有一次真实的 `ctx.agents.resume`；师父点了「去客厅」，会话这边一点反应都没有，就是因为这行代码永远等不到执行的那一刻。

**对法**：休眠时还得能跑的东西，只能挂在「不属于任何一轮」的地方：

- 插件装载时起的定时器：`apply()` 里 `setInterval`（20 秒），`unref()` + `ctx.effect(() => () => clearInterval(tick))` 收尾；
- 或者外部程序回调：房间进程自己来叫 DSH，不经这一轮；
- `pre-step` 只做它该做的——记下这一轮的会话 id（`lastSid`），供定时器使用。

**怎么验**（不许靠感觉）：

1. 定时器真跑了吗：在回调里打一行带时间的日志，看它是不是每分钟都在；
2. 有没有一次真实的 `ctx.agents.resume`：看会话是不是**因为外部事件自己起了一轮**，而不是我打完这句话它才动；
3. 冷却吃没吃掉：3 分钟内只该叫一次，多叫就是没锁住。

**判据一句话**：要「叫醒」的东西，不能依赖「已经醒着」；钩子得挂在钩子真的会跑的那一刻。

## 别在进程里 resume 自己这个会话（2026-11-12 定）

**现象**：房间一有动静就新出一个 `crash-*-host.log`，两分钟一次。日志只有一行是致命的：

```
dsh: fatal load failure: SessionAlreadyOwnedError: session "…" is already owned by an active write handle
  at JsonlBackendTracker.claimWrite (dsh-session-persistence-jsonl/lib/index.js:315:35)
  at Proxy.open (…/lib/index.js:2520:16)
```

**对账**：`唤醒账.jsonl` 里每一条「叫醒：…」都比一份崩溃日志早 0.6~0.8 秒
（00:37:31.086 / 00:40:26.061 / 00:41:41.667 / 00:42:36.755 四次全中）。
所以不是外部两开、不是环境没装，是**我调 `ctx.agents.resume(sid)` 去叫醒自己**。

**为什么**：`claimWrite` 是进程内的写句柄登记。这个会话已经开着、握着句柄，
再 resume 同一个 id 就再开一次 backend → 撞上自己 → 宿主 fatal，当场 exit 1。

**对法**：

- 同进程里**不 resume 自己**。要叫醒，交给外部进程（房间 / 桥的服务）去投递；或
- 只落盘：写 `唤醒待办.jsonl`，段里 `renderWakeTodo` 显示「该叫醒：…（未抢句柄，等你开口）」，
  等宿主下一轮把它带进来；
- 验证顺序：`唤醒账.jsonl` 里出现「该叫醒（未抢句柄）：…」且**没有**新出 `crash-*`。

**判据一句话**：叫醒的代价不能是把这个会话杀掉——抢句柄的路，看上去像叫醒，其实是自杀。
